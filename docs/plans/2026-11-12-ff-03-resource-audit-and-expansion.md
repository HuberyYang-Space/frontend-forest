# FF-03 资源核验与分类扩充实施计划

> 执行时使用 `superpowers:executing-plans`，按任务推进并记录验收结果。若用户选择分工执行，再使用 `superpowers:subagent-driven-development`。

**状态** 2026-11-12 已完成，已提交并发布；浏览器 DOM/console 验证已授权。

**Goal:** 先完成原 FF-03 三条待办，再全面检索并补全前端框架、生态、构建、CSS、测试与代码规范资源。

**Architecture:** 沿用静态 TypeScript 清单和现有卡片消费链路，以分类覆盖表驱动研究与收录。版本、维护状态及收录依据记录在核验文档；界面只保留现有字段，必要的维护状态说明写入简介。

**Tech Stack:** Vue 3、TypeScript、Vite、Element Plus、Node.js、pnpm；使用项目现有依赖。

**Spec:** [本计划的需求与方案](#需求与方案)，依据 2026-11-12 用户确认的范围编写。

## 全局约束

- 严格保持顺序：现有条目核验、修正、验收全部完成后，才开始全网搜索新增项目。
- 收录活跃且知名的项目；知名但维护停滞的项目，只有仍有大量用户的证据时才保留。原有项目同样适用。
- 框架、库、工具核对最新稳定版、对应文档及后继项目；知识站检查维护与内容时效。用户已允许收录 Beta/实验项目，简介须明确标注阶段。
- 官方入口优先；允许仍在维护、来源可追溯的社区中文文档。页面实际没有中文内容时不提供中文入口。
- 测试和代码规范纳入；编辑器与设计素材另排。
- 不预设新增数量上限。以覆盖表、候选逐项结论和交叉检索结果评估完整性，不声称能证明全网绝对穷尽。
- 已有依赖不升级；不为了数据整理引入测试框架，不新增没有界面消费者的版本或审核字段。
- 保护主目录原有的 [tsconfig.json](../../tsconfig.json) 修改。产品代码实施前按 worktree 技能核实隔离方式。
- 浏览器调用须先获得用户对本任务的授权；页面结论以 DOM 和 console 为准。不得要求用户切到前台或保持窗口可见。
- 发现未确认的关联范围、例外或分类归属时先询问，相关条目显式标为待决。
- 提交、推送和生产发布不属于本计划的默认动作；用户要求提交时使用 `commit` 技能。

## 重点复核

1. HTTP 200 实际返回停放页、登录页、错误页或错误项目：检查内容与官方来源，不只检查状态码。
2. 社区中文站停更，或中英文入口指向同一英文页面：分别核对语言、版本和翻译维护情况。
3. 项目改名、迁移、合并或停止维护：保留版本与后继关系证据，避免重复收录或仅凭 Stars 保留。
4. 扩充后出现重复 ID、失配入口或卡片未被消费：实际导入数据，并核对页面卡片与链接 DOM。
5. 长名称、多标签和图标失败：真实浏览器检查窄屏布局、链接入口及 console；不将 Node 检查当作布局验收。

## 需求与方案

### 已确认的需求

1. 完成 [原 FF-03 三条待办](../TODO.md#ff-03-全面核验并更新资源链接)：逐条核验现有链接，修正信息，记录并验证目录读取与构建。
2. 随后全网搜索现有分类中的高活跃、高知名项目，补全资源列表。
3. 新增 CSS 类，覆盖预处理器、CSS 框架与知识资源。
4. 核对不活跃项目的最新版本及替代情况；知名且仍被大量使用的项目可保留。
5. 官方中文优先，允许经核验的社区翻译。
6. 测试与代码规范纳入，编辑器与设计素材另排。

### 分类方案

用户已确认保留现有两类，新增 CSS，并为测试与代码规范增加第四类。

| 展示分类       | 检索覆盖面                                                                                                   |
| -------------- | ------------------------------------------------------------------------------------------------------------ |
| 框架与生态     | UI 框架、应用框架、路由、状态管理、数据请求与缓存、UI 组件库、跨端框架，以及与前端开发直接相关的运行时生态   |
| 打包/构建工具  | 开发与构建工具、打包器、编译与转译、压缩、任务编排及构建缓存                                                 |
| CSS 相关       | 预处理器、CSS 处理与优化、原子化与传统 CSS 框架、CSS-in-JS、样式基础库，以及文档、教程、规范和兼容性知识资源 |
| 测试与代码质量 | 单元与组件测试、端到端与浏览器测试、测试配套，以及 lint、格式化和代码规范工具                                |

跨分类项目只建立一个主体条目，通过标签说明能力；不同职责、拥有独立文档与用户群的同生态项目可分别收录。CSS 专属的处理工具与知识入口优先归入 CSS 类。

### 实现取舍

- 采用人工审校的静态清单：保持现有数据契约，通过来源记录与验证保证质量，适合本轮资源整理。
- 不采用自动抓取结果直接入库：热度、页面归属、中文时效和后继关系需要逐项核实；抓取结果只作为候选线索。
- 不新增动态目录服务：当前页面已直接循环读取资源分组，增加分类和资源可复用这条生产链路。

### 收录证据

- **活跃度：** 核对最近 12 个月的稳定发布、维护公告及近 90 天实质维护情况，记录事实与日期。不同类型不套用统一发布频率；提交次数只是辅助信号。
- **知名度与使用量：** 结合官方生态推荐、当前可获得的使用调查、包下载、依赖使用和仓库数据。不同生态不机械套用同一个 Stars 或下载阈值。
- **维护停滞但仍广泛使用：** 同时提供项目状态与当前使用量证据，并在简介说明适用状态；仅有历史名气不能作为保留依据。
- **知识资源：** 以权威性、内容更新及覆盖价值判断，不以 npm 数据或项目版本要求知识站。
- 每个项目记录最新稳定版本或知识站更新情况、官方来源、中文来源性质、维护及使用证据、核验日期、收录结论和分类。能定位到来源的数值才写入记录。
